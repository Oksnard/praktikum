# Сверка UNKNOWN/PENDING и незавершённого резерва

Это runbook оператора, не выполненная корректировка. Первоначальный OpenAI UNKNOWN `efc6746b-d603-495c-9dcd-be03ae1e5443` остаётся без изменений. Более поздний отдельный429 не доказывает исход первоначального запроса и не разрешает объявить его бесплатным.

## Почему нельзя использовать operation.cost как стоимость текущего раунда

Один request_hash после явного REJECTED может выполняться несколько раз. `AiOperation.cost` накапливает **все известные стоимости всех раундов**, а резерв относится только к одному ещё не закрытому раунду. Каждый раунд имеет UUID в ledger keys:

- `reserve:<operationId>:<reservationId>` — отрицательное R;
- `settle:<operationId>:<reservationId>` — возврат R−C текущего раунда.

Ранние записи до введения retry rounds используют `reserve:<operationId>`/`settle:<operationId>`; их можно сопоставлять только после проверки единственного исходного раунда. Успешные завершённые раунды повторно не корректируются.

## Обязательные условия

1. Сделать backup. Остановить только процессы API Практикума/дождаться завершения запросов, чтобы PENDING действительно не принадлежал живому запросу. Не трогать чужие сервисы.
2. Зафиксировать operation id, tenant, user, status, revision, request_hash, requested model/provider/tariff version, все AiCall и ledger rows. Установить один outstanding reserve: соответствующего settle key ещё нет. Несколько несопоставимых резервов — остановиться и исследовать, не суммировать наугад.
3. Получить доказательство **именно этого запроса** у провайдера: request id/usage record/однозначный rejection. Похожая ошибка другого запроса, balance dashboard и отсутствие результата не доказывают нулевой usage. Неизвестность сохраняет резерв.
4. Стоимость рассчитывается по внутреннему тарифу нужной версии из фактических токенов/кэша каждого вызова; DeepSeek invoice discount не подменяет фиксированный внутренний каталог. Разные provider/model/tariff hashes не смешиваются.

## Арифметика

- **R** = отрицание outstanding reserve.amount, а не текущая глобальная константа. Старые операции могут резервировать100000, новые200000.
- **S** = стоимость уже закрытых раундов: сумма `(−reserve.amount) − settle.amount` только по сопоставленным завершённым парам этой операции.
- **K** = уже зааудированная известная стоимость вызовов текущего открытого раунда. Время ledger reserve и AiCall помогает разделить раунды; проверять согласованность с S и cumulative operation.cost. Если корреляция неоднозначна, не менять деньги.
- **U** = дополнительно доказанная стоимость ранее неизвестного вызова/вызовов текущего раунда.
- **C = K + U** = итог текущего раунда.
- **Возврат = R − C**. Company.balance увеличивается на возврат; User.spent уменьшается на тот же возврат.
- **Новая cumulative operation.cost = S + C**, а не C и не прежний operation.cost плюс C (последнее повторно учтёт K).

Пример: прошлые раунды S=270; текущий резерв R=200000; до сетевой ошибки известны K=540; провайдер подтвердил ещё U=300. Итог C=840, вернуть199160, cumulative cost1110. До сверки operation.cost мог быть810 (=270+540). Использовать810 как цену текущего раунда неверно.

Если C>R, не допускать отрицательного баланса/расходов и не обходить CHECK. Это нарушение ожидаемой границы тарифа/usage либо ошибка корреляции: отдельное расследование и утверждённая учётная корректировка. Нельзя списывать vendor invoice USD по другому тарифу как внутренние кредиты.

## Одна атомарная корректировка

После доказательств оператор в одной DB transaction блокирует строку операции и проверяет неизменность ожидаемых status/revision. Повторно проверяет отсутствие **точного** settlement key outstanding раунда, затем:

1. Дописывает проверяемый audit evidence с источником и ответственным оператором. Исторический USAGE_UNKNOWN не переписывается задним числом.
2. При наличии usage именно неизвестного вызова добавляет его отдельный audit, не дублируя ранее записанные K. Если есть только общая денежная сумма без token usage, нельзя выдумывать AiCall token counts: это отдельная ручная учётная корректировка с явным объяснением.
3. Записывает возврат R−C в CreditTransaction с уникальным **каноническим settle key** этого раунда и видом MANUAL_RECONCILIATION. Этот же ключ защищает от повторной корректировки/запоздалого штатного settlement.
4. Согласованно обновляет Company.balance, User.spent и cumulative operation.cost=S+C. Проверяет tenant/user совпадения, nonnegative guards и сумму ledger.
5. Фиксирует terminal status согласно доказательству: REJECTED при подтверждённом отказе (допускает явный новый retry); FAILED при известном невалидном/потерянном результате; SUCCESS только если есть сохранённый ответ и повторная проверка текущих source/criteria/Zod/evidence. Не придумывать результат для успеха. Для повторной публикации assignment/attempt соблюсти operationId uniqueness.

После commit проверить ledger, balance, spent, audit totals, статус и отсутствие outstanding reserve; сохранить протокол до/после. Только затем возобновить API. Проверка нового retry выполняется отдельно, не пересылая неизвестный запрос автоматически.

Ни SQL исправлений, ни возврата первоначального UNKNOWN в этой сессии не выполнялось. Не автоматизировать этот runbook без отдельного reconciliation интерфейса и тестов crash/replay.
