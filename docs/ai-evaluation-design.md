# Оценка конкретного задания, V2

Новые задания содержат `version:2` и неизменяемый `assessment` вместе с вопросом: 3–6 требований, уникальный id, один из критериев, формулировка, точная цитата исходного материала и точная цитата вопроса. Это ответ того же вызова генерации, не дополнительный платный запрос. Критерии компании копируются в Assignment как прежде: accuracy40/completeness30/application30.

Генератор выбирает требования применительно к вопросу. Уже выполненный шаг, условие, которое не наступило, или необязательная деталь не становятся обязательной частью ответа. Правило описывает результат и ограничения, допускает разные корректные способы и смысловые перефразы. Клиент видит тот же вопрос; данные сохранены в JSON content, миграция таблиц не нужна.

Оценщик получает source, question со snapshot, answer и criteria. Сначала соотносит каждый пункт с полным ответом, затем выставляет три отдельных балла. `checks` содержит rule_id, met/partial/missing/contradicted, короткие дословные answer_quotes и объяснение. Для missing цитат нет, для остальных статусов есть хотя бы одна. Сервер требует все уникальные сохранённые id, проверяет принадлежность цитат ответу, source evidence, границы критериев и точную сумму.

Факт регламента отличается от предложенного сотрудником плана. Например, действие раньше предельного срока или выбранное время следующего сообщения не становится неподтверждённым правилом компании. Нельзя объявлять пропущенным действие, которое выражено иначе или находится в другой части ответа. Policy5 также различает учебный план и выполненную операцию: если значение отсутствует в условии, намерение взять фактическое значение из надёжного источника или шаблон засчитывается, выдумывать значение нельзя. Каждый check ограничен собственным requirement; посторонняя деталь источника не добавляется к нему как повод штрафовать. Точность, полнота запрошенных применимых действий и применение к ситуации оцениваются отдельно. feedback/gaps/recommendations должны соответствовать найденным дефектам; положительному ответу не придумываются недостатки.

## Совместимость и границы

- Старые строгие AssignmentSchema/EvaluationSchema сохранены. StoredAssignmentSchema/StoredEvaluationSchema читают обе версии. Записанные оценки и их provenance не переписываются.
- Новые операции принимают только V2 с сохранённым assessment и режимом `snapshot`. Новая оценка старого задания отклоняется409 до резерва, создания операции и provider call. Владелец/руководитель нажимает «Обновить задание»: существующая генерация создаёт новый вопрос и snapshot, старое задание и ответы не меняются. Сотрудник видит просьбу обновить задание вместо формы ответа. Исторические V1 и `legacy_question` отчёты доступны с отметкой «Предыдущая методика».
- Hash policy version5 инвалидирует cache предыдущих промптов; input содержит snapshot и режим. SUCCESS replay по-прежнему бесплатен, failed terminal для того же hash, revision CAS и settlement не менялись.
- Prompt module: [ai-prompts.ts](../apps/api/src/ai-prompts.ts). Общий подход не содержит доменных словарей CRM/лаборатории/информационной безопасности. Никакой второй модели-критика или fixture fallback.
- Exact quote/coverage checks доказывают структуру и происхождение цитат, **не** логическую правильность вывода. Смысловую релевантность требования и связь цитаты с вердиктом оценивает модель; возможны ошибки. Проверку кадровых решений выполняет человек.

## Вывод, бюджет и аудит

Оба провайдера ограничены 4096 output tokens. Промпт требует короткий отчёт. `finish_reason` кроме stop возвращает невалидный audit payload с raw content и причиной; даже синтаксически завершённый JSON на границе length не публикуется. Usage такого ответа учитывается как INVALID. До двух повторов, всего максимум три вызова. Network outcome с неизвестным usage остаётся UNKNOWN с удержанным резервом.

Перед резервированием проверяется **полностью сериализованное тело самого длинного запроса**: system policy, user input, JSON schema (в system для DeepSeek / response_format для OpenAI), параметры и retry instruction. UTF8 размер не более200000 байт; превышение отклоняется целиком, без усечения. Тот же guard работает непосредственно перед SDK вызовом.

Консервативная оценка для поддерживаемых byte-based tokenizers: не более одного токена на UTF8 байт плюс1024 токена на framing. При самом дорогом внутреннем тарифе DeepSeek и без cache скидки:

`ceil((201024 × 300 + 4096 × 1200) / 1000) × 3 = 195669` кредитов.

Резерв200000 сохраняет4331 кредит запаса. Это bound при заявленных tokenizer/framing assumptions, а не гарантия против изменения внешнего провайдера; при изменении моделей/тарифов/SDK framing пересчитать. Unit строит полные запросы обоих видов обоим провайдерам ровно на byte boundary и проверяет отказ на+1 байт и стоимость трёх максимальных вызовов. Реальные входы с source12000/answer8000 значительно короче этого предела. Тарифы не изменены.

## Проверки

25 unit tests включают3 human-authored domain fixtures (поддержка/рабочие часы, хранение лабораторных образцов, отзыв скомпрометированного токена), допустимые варианты, неприменимые условные обязанности, выдуманные source/answer quotes, дубли/неполное покрытие правил, неверную сумму, legacy, truncation и request budget. Эти fixtures — авторские контракты/ожидания, **не** результаты модели и не доказательство её качества в трёх доменах.

HTTP e2e с DI доказывает409 на новую оценку старого задания без изменения баланса/spent/ledger/operations/calls; запрет обновления сотрудником403; новыйV2id при обновлении владельцем/руководителем и неизменность старых записей. Также проверяет генерацию V2 → оценку V2, invalid retries/billing, cache, tenant isolation, limit/reserve, UNKNOWN и ABA CAS. Реальные семантические результаты отдельно в [AI quality review](ai-quality-review.md). Старые пять live snapshots остаются историческими; их диапазоны не доказывают устранение найденных ложных штрафов.
